# Swap 安全与工程风险

Swap 合约看起来只是“用户给一种 Coin，合约返回另一种 Coin”，但真正上线时会遇到价格、权限、精度、流动性和并发等风险。本章把前面各章的安全点集中整理。

## 本章目标

- 建立 Swap 合约的安全检查框架
- 理解固定汇率、AMM、订单簿的不同风险
- 掌握滑点、精度、权限和事件记录的工程要求
- 为生产级项目建立审计清单

## 储备耗尽

固定汇率模型最大的问题是储备可能被换空：

```move
let usd_balance = bank.usd.split(amt_usd);
```

如果 `bank.usd` 不足，交易会失败。生产项目至少需要：

- 在兑换前检查储备
- 给用户清晰错误码
- 支持用户设置最小输出
- 避免固定价格长期偏离市场价格

## 滑点保护

AMM 中用户收到的数量会随交易规模变化。如果没有 `min_out`，用户可能在价格波动后收到远少于预期的资产。

推荐接口形态：

```move
public fun swap_x_to_y<X, Y>(
    pool: &mut Pool<X, Y>,
    coin_in: Coin<X>,
    amount_in: u64,
    min_out: u64,
    ctx: &mut TxContext
)
```

合约内部必须断言：

```move
assert!(amount_out >= min_out, EHaveSlippage);
```

## 精度损失

Move 中没有浮点数，DeFi 计算通常使用整数乘除。风险包括：

- 除法向下取整
- 小额交易被舍入为 0
- 中间乘法溢出
- 手续费计算顺序导致误差

工程建议：

- 中间计算尽量使用 `u128`
- 先乘后除，但要检查上限
- 明确最小交易额
- 给手续费和 LP 份额写单元测试

## 价格操纵

AMM 的价格来自池内储备。攻击者可以通过大额交易短暂推高或压低价格。如果其他协议直接读取池内价格作为预言机，就可能被操纵。

防护方式：

- 不把即时池价直接当预言机
- 使用 TWAP 或外部预言机
- 对大额交易设置滑点和限额
- 对关键操作加入时间窗口或多源价格验证

## 管理员权限

示例中常见 `AdminCap`、`TreasuryCap`、`DenyCapV2`。这些对象一旦被单个私钥控制，就存在中心化风险。

生产项目建议：

- 使用多签地址持有关键 Cap
- 对敏感操作发事件
- 明确权限转移流程
- 避免把无限铸造能力共享出去
- 对暂停和黑名单能力写入文档

## 共享对象并发

Sui 的对象模型支持并行执行，但 shared object 会进入共识路径。热门池子、订单簿和全局配置对象都是共享对象，可能成为性能瓶颈。

工程建议：

- 把全局配置和池子状态拆开
- 每个币对使用独立 Pool
- 避免所有操作都写同一个全局对象
- 用事件记录历史，不要把所有历史塞进对象字段

## 事件与可观测性

生产级 Swap 至少应发出：

- 创建池子事件
- 添加流动性事件
- 移除流动性事件
- Swap 事件
- 管理员参数变更事件
- 手续费提取事件

事件不是装饰，而是前端、索引器和审计系统理解协议状态的基础。

## 审计清单

| 检查项 | 问题 |
|--------|------|
| 权限 | 谁能 mint、withdraw、pause、deny |
| 滑点 | 所有 swap 是否支持 `min_out` |
| 溢出 | 是否使用 `u128` 处理中间乘法 |
| 舍入 | 小额交易是否会输出 0 |
| 储备 | `split` 前是否检查余额 |
| 事件 | 关键状态变化是否 emit |
| 测试 | 是否覆盖边界值和失败路径 |
| 对象 | shared object 是否过度集中 |
| 升级 | 包发布后如何处理迁移 |

## 本章小结

教程合约用于理解模型，生产合约必须补齐安全边界。Swap 的核心风险集中在价格、权限、精度和共享对象状态上。写 DeFi 合约时，不应只问“公式是否正确”，还要问“极端输入、恶意交易和权限泄露时会发生什么”。
